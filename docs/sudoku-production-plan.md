# Sudoku Production Plan

Updated: 2026-06-18

This document tracks the remaining work needed to make PuzzleHub's Sudoku slice production-ready before expanding to other games.

## Progress Snapshot (2026-06-18)

- Phase 0 (Architecture): complete.
- Phase 1 (Sudoku Quality): complete — full technique-based rater, solving-profile rating, 1k-seed nightly stress, cross-runtime determinism (Node ≡ workerd), performance budgets.
- Phase 2 (Mobile Local-First): playable + local-first; remaining items are store assets and reviewed launch copy.
- Phase 3 (API & Security): `/v1` versioning, strict DTOs, rate limits, log redaction, coarse complete done; object-level auth still pending.
- Phase 4 (Sync): server engine + idempotent `/v1/sync` + D1 store; mobile outbox flush/backoff + conflict UI done. Remaining: remote D1 migration apply.
- Phase 5 (Daily Publishing): complete — immutable published dailies, admin preview/publish/status, audit, missing-daily cron.
- Phase 6 (Retention): server-validated completions, stats/streaks, deterministic achievements, leaderboard with pseudonyms — all acceptance criteria met. Remaining: excessive-attempts/replay-mismatch anti-cheat.
- Phase 7 (Testing & CI): PR workflow runs the full verification chain (install/format/lint/typecheck/test/builds); nightly generator stress exists. Remaining: Worker runtime tests (Miniflare/D1), mobile unit + web E2E, artifact upload.
- Worker test seams are in-memory; the D1 adapters are validated via `bun:sqlite` migration checks. Remote `wrangler d1 migrations apply` for `0002`–`0006` is still pending (needs valid Cloudflare auth).

## Core Principles

- Finish Sudoku quality before expanding the game surface.
- Keep shared game rules in `packages/game-core`.
- Keep Sudoku generation, solving, rating, and validation in `packages/sudoku-engine`.
- Public Worker responses must never expose puzzle solutions.
- Prefer local-first mobile behavior; sync is backup and reconciliation.
- Add tests for every puzzle generator before wiring it into the app.

## Phase 6: Retention Systems

- `[x]` Implement server-side score calculation on complete.
- `[x]` Persist completion events.
- `[x]` Queue stats aggregation. (Queue consumer replays a device's completion events into `device_stats`; served at `GET /v1/stats?deviceId=`.)
- `[x]` Queue streak updates. (Current/longest streak computed in the same replay, using the UTC streak-day rule.)
- `[x]` Queue achievement evaluation. (Consumer replays a device's events through `evaluateAchievements` and persists unlocks to `device_achievements`; served at `GET /v1/achievements?deviceId=`.)
- `[x]` Queue leaderboard rebuild or incremental update. (Consumer rebuilds all-time + daily boards from the event log into `leaderboards`; served at `GET /v1/leaderboard`.)
- `[x]` Define timezone rule for daily streaks. (MVP: a streak day is the UTC calendar day of the completion timestamp; documented in `statsAggregation.ts`.)
- `[x]` Add XP rules.
- `[x]` Add first achievement set:
  - `[x]` First solve
  - `[x]` First daily
  - `[x]` No-mistake solve
  - `[x]` 3-day streak
  - `[x]` 7-day streak
  - `[x]` Hard puzzle completed
- `[~]` Add anti-cheat flags for unrealistic completion time, duplicate submissions, excessive attempts, and replay mismatch. (Unrealistic time, duplicate submissions, and excessive mistakes/hints flagged on each completion, and flagged completions are excluded from leaderboards; excessive-attempts and replay-mismatch need the attempt/move history.)
- `[x]` Use pseudonymized leaderboard display names.

Acceptance criteria:

- `[x]` Stats and streaks can be replayed from completion events. (`replayStats` folds the append-only log into `device_stats`; the queue consumer literally replays a device's events, so aggregation is idempotent and always reproducible.)
- `[x]` Achievements are deterministic. (`evaluateAchievements` is a pure fold over the event log; the same events always unlock the same achievements with the same timestamps.)
- `[x]` Leaderboard entries come only from server-validated completions. (Boards are rebuilt from the `completion_events` log — recomputed scores only, client scores never trusted — and flagged completions are excluded.)
