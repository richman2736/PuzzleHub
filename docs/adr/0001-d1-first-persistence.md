# ADR 0001: D1-First Persistence For MVP

Date: 2026-06-16

## Status

Accepted

## Context

PuzzleHub's first production slice is Sudoku. The mobile app is intentionally local-first:
players can continue without a server response, and sync is backup plus reconciliation.

The backend runs on Cloudflare Workers. The existing `packages/db` schema was PostgreSQL-oriented,
but the current MVP needs a small relational store close to the Worker, with low operational
overhead and straightforward deployment.

## Decision

Use Cloudflare D1 as the MVP persistence layer.

Postgres remains an escape hatch if later requirements outgrow D1, especially for heavy analytics,
large admin queries, cross-game reporting, or operational needs that are better served by a
dedicated Postgres provider through Hyperdrive.

## Consequences

- `packages/db` uses Drizzle's SQLite schema primitives.
- Worker config owns D1, Queue, and rate-limit bindings through `wrangler.jsonc`.
- Public API responses must continue to use allowlisted DTOs and must not expose Sudoku solutions,
  even though server-side puzzle rows store `solution_data`.
- IDs are generated by application code, not by database-specific UUID defaults.
- JSON payloads are stored as SQLite text JSON through Drizzle and D1-compatible SQL migrations.
- D1 database IDs in `wrangler.jsonc` are placeholders until real resources are created with
  `wrangler d1 create`.

## Follow-Up

- Create real D1 databases for dev, staging, and production.
- Replace placeholder database IDs in `apps/worker/wrangler.jsonc`.
- Apply `packages/db/migrations/0001_initial.sql` locally and then remotely.
- Add Worker runtime tests using local D1/Miniflare or Cloudflare Vitest pool.
- Implement idempotent sync endpoints before using D1 as source of truth for mobile state.
